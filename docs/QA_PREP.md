# 專題 QA 準備文件 — BCI × YouTube Music

> 給組員 QA 前快速複習用。涵蓋系統架構、實作細節、設計取捨，以及最可能被問到的問題與標準答案。
> 所有數字都對應現行程式碼（`bci_server.py` / `train_compare.py` / `bci-ytm-extension/`）。

---

## 0. 一句話講清楚這個專題

> 用單通道腦波儀（BrainLink Lite, Fp1）即時感測腦波，透過「連續眨眼的持續時間」控制 YouTube Music 播放，並依「專注/放鬆」狀態做情境式歌單過濾，外加 LLM 即時教練回饋。

---

## 1. 系統架構（三層 + 一條 WebSocket）

```
① 訓練（離線，一次性）
   bci_dataset_114-2_update（18人→排除2人=16人）
   → train_compare.py（5 模型 LOSO 比較）
   → save_best_model.py → bci_model.pkl（MLP，0.2MB）

② Python 後端（即時）  bci_server.py
   訊號來源 signal_sources.py（brainlink / file / dummy / folder）
   → 4 秒滑動視窗 → 12 維特徵 → RobustScaler → MLP 推論
   → 眨眼偵測（兩種模式，見 §4）→ 動作判定
   → WebSocket 廣播 JSON (ws://localhost:8765)
   → LLM 教練 llm_coach.py（OpenAI，選用）

③ Chrome 擴充  bci-ytm-extension/
   注入 music.youtube.com → 收 WebSocket → 畫 overlay
   → 點頁面播放鈕 / 情境過濾切歌 / 顯示 AI 教練
```

**設計核心：三層完全解耦。** 後端不知道音樂在播什麼，擴充不知道腦波怎麼來，中間只靠 WebSocket JSON 溝通。好處：要換成 Spotify 只需改擴充、要換感測器只需改 `signal_sources.py`。

## 2. 資料集與訊號

| 項目 | 值 |
|---|---|
| 感測器 | BrainLink Lite，單通道，電極位置 Fp1（前額） |
| 取樣率 | 512 Hz |
| 任務 | 3 類：Relax（放鬆）/ Focus（專注）/ Blink（連續眨眼） |
| 受試者 | 18 人，每人每任務 30 試次，每試次 20 秒 |
| 訓練用 | 排除 S13（準確率=亂猜 0.33）、S14（<0.6）後 = **16 人** |

**為什麼排除 S13/S14：** 用全 18 人先跑一次 LOSO，發現這兩人準確率接近隨機（三任務頻帶分布幾乎一樣 = 訊號無可分性，可能配戴不良或沒真的切換狀態）。排除後整體 +4~9%、標準差砍半。

## 3. 特徵工程與模型

### 12 維特徵（每個 4 秒視窗）
1. **5 維頻帶相對功率**：Delta/Theta/Alpha/Beta/Gamma（FFT → 各頻帶能量佔比 → log+sqrt）
2. **3 維 Hjorth 參數**：Activity / Mobility / Complexity（訊號複雜度）
3. **1 維標準差**
4. **3 維新增特徵**：Alpha/Beta 比值（警覺度指標）、峰峰值（眨眼幅度）、過零率（頻率密度）

前處理：1–40 Hz FFT 帶通 + RobustScaler（抗離群值，對眨眼大尖峰穩健）。

### 模型比較（16 人 LOSO，更新版資料集）
| 模型 | 準確率 | 標準差 |
|---|---|---|
| **MLP（部署）** | **0.879** | ±0.116 |
| SVM (Linear) | 0.876 | ±0.110 |
| Ensemble (RF+SVM+LDA) | 0.869 | ±0.116 |
| RandomForest | 0.868 | ±0.122 |
| LDA | 0.851 | ±0.105 |

部署 MLP：準確率最高、推論最快、檔案最小（0.2MB vs Ensemble 45MB）。

**LOSO（Leave-One-Subject-Out）：** 每次拿 15 人訓練、留 1 個「完全沒看過的人」測試，輪 16 次平均。這比隨機切分嚴格，反映「對新使用者」的真實泛化能力。

## 4. 眨眼控制邏輯（重點，必考）

動作對應（依**連續眨眼持續秒數**分桶）：
| 持續時間 | 動作 |
|---|---|
| < 2 秒 | 忽略（過濾生理性眨眼） |
| 2 – 4 秒 | 播放 / 暫停 |
| 4 – 6.5 秒 | 下一首 |
| 6.5 – 9 秒 | 重播本曲 |
| > 9 秒 | 忽略（訊號黏住/沒及時停） |

**系統有兩種眨眼偵測模式（CLI `--control-mode`）：**

- **`raw`（目前預設）**：直接看 Fp1 原始訊號的峰峰值振幅，超過自適應門檻就算「正在眨眼」，量持續時間。理由見 §6 Q4。
- **`model`**：用 MLP 的 Blink 機率 + hysteresis 狀態機（進入門檻 0.55 / 離開 0.40）判斷眨眼狀態。

**為什麼用「持續時間」不用「眨眼次數」：** 實測同學的「眨 N 次」資料，用尖峰計數當分類器精確準確率只有 23%（接近亂猜）——因為 20 秒內會夾雜自然眨眼、單次眨眼有「閉+張」雙峰、訊號抖動，把計數灌爆。改用「連續眨眼持續多久」穩定得多。

## 5. 三大功能

### (A) 眨眼播放控制 — 見 §4

### (B) 情境式歌單過濾（在擴充內，讀後端 relax/focus 機率）
- **過濾模式**：選目標狀態（專注/放鬆），播放中的歌持續一段時間沒讓你進入該狀態 → 自動跳下一首。對應「匯入混雜歌單自動濾掉不對味的歌」。
- **手動切歌單**：兩顆按鈕直接切到預設的專注/放鬆歌單。

### (C) LLM AI 教練（OpenAI gpt-4o-mini，選用）
- **即時解讀**：每 20 秒把腦波趨勢丟給 LLM，回一句中文回饋。
- **Session 報告**：點按鈕 → 分析整段 → 專注度評分 + 觀察 + 建議。
- API key 只讀環境變數，**不寫進程式碼、不上 git**；沒設 key 時整套照常運作，只是教練面板停用。

## 6. 最可能被問的問題與標準答案

**Q1. 你只有一個電極（Fp1），憑什麼分得出專注和放鬆？**
A: Fp1 在前額，能可靠抓到 Alpha 波（放鬆/閉眼時增強，Berger effect）與眼動。專注時 Beta 偏高、Alpha 受抑制；放鬆時 Alpha 主導。我們用 5 個頻帶的相對功率 + Alpha/Beta 比值當特徵，LOSO 跨人驗證 87.9%。單通道確實限制了空間資訊（這也是我們無法做 ICA 去雜訊的原因，見 Q7）。

**Q2. 為什麼用 LOSO 而不是一般的 train/test split？**
A: 一般隨機切分會讓「同一個人」的資料同時出現在訓練和測試，模型可能只是記住個人特徵，準確率虛高。LOSO 強制「測試的人完全沒出現在訓練集」，反映對新使用者的真實表現。這是 BCI 領域標準做法。

**Q3. 為什麼最後部署 MLP 不是準確率也很高的 Ensemble？**
A: MLP 準確率最高（0.879）、推論最快、模型檔最小（0.2MB vs Ensemble 45MB）。差距 1% 內但工程成本差很多，所以選 MLP。（補充：舊版資料集時是 Ensemble 略勝，換資料後 MLP 反超——我們是用實驗數據決定，不是憑感覺。）

**Q4. 你訓練了模型，為什麼眨眼控制預設用 raw 振幅偵測而不是模型？**
A: 這是刻意的工程取捨。模型的 4 秒視窗時間解析度太粗、又有機率平滑延遲，對「眨眼開始/結束的精確時間點」不夠靈敏；而眨眼在 Fp1 是 200–500µV 的明顯大尖峰，直接看 raw 振幅又快又準又即時。模型負責「整體狀態分類（專注/放鬆）」用於情境過濾，raw 偵測負責「眨眼計時」用於控制——各司其職。兩種模式都保留，可用 `--control-mode` 切換。

**Q5. 「連續眨眼幾秒」這種控制方式會不會很難用 / 容易誤觸？**
A: 我們有多重防呆：(1) < 2 秒的眨眼直接忽略（過濾自然反射）；(2) hysteresis 雙門檻防抖；(3) > 9 秒視為訊號異常忽略；(4) 動作觸發後有冷卻時間。overlay 上有即時進度條讓使用者看到自己停在哪個動作桶，所見即所得。

**Q6. 為什麼「上一首」變成「重播本曲」？**
A: 誠實面對技術限制。YT Music 的上一首按鈕第一次按只會把當前曲目跳回開頭，要按第二次才真的換歌，但第二次點擊在頁面上不穩定（我們試過比對歌名重點，仍不可靠）。與其給一個時靈時不靈的功能，不如定位成穩定可用的「重播本曲」。

**Q7. 眨眼是很大的雜訊，會不會污染你的頻率特徵？有沒有做去雜訊（如 ICA）？**
A: 會污染，這是真問題。但 ICA 需要多通道（≥8 電極）做空間分離，我們是單通道硬體，數學上做不了 ICA。我們的緩解方式：(1) RobustScaler 對極端值不敏感；(2) 4 秒視窗平均稀釋瞬間眨眼的影響；(3) 模型直接把眨眼當成第三個類別一起學。未來若升級多通道 EEG 就能加 ICA。

**Q8. WebSocket 架構的好處？為什麼不全做在一支程式？**
A: 解耦。腦波處理需要 Python（scikit-learn），但控制 YT Music 必須在瀏覽器內（操作頁面 DOM）。WebSocket 讓兩邊各用最適合的技術、獨立開發測試。換播放器只改擴充、換感測器只改後端訊號層。

**Q9. LLM 教練是噱頭嗎？腦波資料真的餵給 GPT？**
A: 真的餵。我們把 session 的腦波狀態時序（每分鐘主導狀態、專注比例、操作紀錄）組成結構化資料給 gpt-4o-mini，請它產生個人化專注報告。這是 LLM 擅長的多模態綜合分析，本地小模型做不到。成本極低（每次約 NT$0.1–1）。沒設 API key 時系統照常運作。

**Q10. 準確率 87.9% 聽起來不錯，但有些受試者很低？**
A: 對，S01/S06/S09 約 0.67。原因是這幾位的「放鬆」和「專注」腦波本身就幾乎一樣（頻帶 L1 距離只有好的人的 1/3，可能受試時沒真的切換狀態），但他們的「眨眼」仍分得很清楚。由於我們的控制主要靠眨眼，對這些人照樣可用，所以沒排除他們。

**Q11. 即時系統的延遲多少？**
A: 模型每 0.5 秒推論一次，4 秒視窗。眨眼控制用 raw 偵測幾乎即時。情境狀態判斷會有視窗本身的 ~2-4 秒延遲，但情境切歌本來就不需要瞬間反應。

**Q12. 這個能實際應用嗎？**
A: 目前是概念驗證。實用場景：(1) 雙手忙碌時的免手控制（開車、做菜、健身）；(2) 行動不便者的數位輔具；(3) 專注力訓練（搭配 AI 教練的回饋）。限制是單通道精度與配戴便利性，這是消費級 BCI 的共同挑戰。
